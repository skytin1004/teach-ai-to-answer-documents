# Контрольний список публікації

Використовуйте цей контрольний список перед комітом або пушем публічних оновлень.

## Безпека

- Переконайтеся, що в Markdown-файлах, блокнотах, зразках даних або скриптах не записані API-ключі, токени, паролі чи приватні кінцеві точки.
- Зберігайте облікові дані в змінних середовища або керованій ідентичності, а не у зафіксованих файлах.
- Не фіксуйте файли `.env` або виконані файли виводу блокнотів.
- Залиште `.env.example` лише як зразок із заповнювачами.

## Перевірка

Запустіть скрипт перевірки репозиторію:

```powershell
python scripts\verify_notebooks.py
```
  
Запустіть повне локальне безпечне виконання блокноту перед публікацією змін імплементації:

```powershell
python scripts\verify_notebooks.py --execute
```
  
Очікувані перевірки:

- проходження локальних Markdown-посилань  
- проходження валідації JSON блокнотів  
- блокноти не містять збережених результатів або лічильників виконань  
- проходження сканування на шаблони секретів з високим ризиком  
- публічні блокноти виконуються локально  
- робочі матеріали в `drafts/` свідомо пропускаються

## Огляд

- Переконайтеся, що посилання у README статтях ведуть до потрібних файлів.  
- Переконайтеся, що кожна стаття має навігацію по репозиторію та посилання на пов’язані блокноти.  
- Переконайтеся, що робочі матеріали не посилаються з публічних індексів, якщо вони не готові до публікації.  
- Переконайтеся, що шаблони GitHub issues та pull request відповідають робочому процесу репозиторію.  
- Переконайтеся, що результати перевірок у статті відповідають останньому результату блокноту.  
- Переконайтеся, що GitHub Actions workflow має виконуватися після пушу.  
- Переконайтеся, що `CHANGELOG.md` відображає оновлення, яке публікується.  
- Переконайтеся, що `CONTRIBUTING.md` все ще відповідно відображає робочий процес репозиторію.

## Git

- Перегляньте `git status --short --branch`.  
- Перегляньте `git diff --stat`.  
- Комітьте і пуште лише коли ви явно готові.
